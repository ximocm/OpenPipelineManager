# Publishing on GitHub

Releases are built by the [release workflow](CI.md#release-workflow) and
published manually from the draft it creates. This guide records the artifact
names, the contents of every package, and the maintainer-only notes that the
packaging scripts rely on.

## Artifact names

`<v>` below is the version without the leading `v` (for example `0.2.0`):
the value that `core/Cargo.toml` `[workspace.package].version` and
`ui/Cargo.toml` `[package].version` must share, and that the tag `v<v>`
must match.

| Platform | Files | Script |
| --- | --- | --- |
| Linux x86_64 | `opm-<v>-linux-x86_64.tar.gz` | `scripts/package-linux.py` |
| Windows x86_64 | `opm-<v>-windows-x86_64.zip`, `opm-<v>-windows-x86_64.msi` | `scripts/package-windows.py` |
| macOS Apple Silicon | `opm-<v>-macos-aarch64.tar.gz`, `opm-<v>-macos-aarch64.dmg` | `scripts/package-macos.py` |

Inside CI the artifacts keep the platform names `linux-x86_64`,
`windows-x86_64` and `macos-aarch64`; they are retained for 14 days so a
package can be reviewed from a pull request without publishing a release.
The release workflow merges the three artifacts and attaches the files
above, plus `SHA256SUMS`, to the draft release.

## What each package contains

Every package stages the same documentation and license set next to its
binary:

- the application: `opm` (Linux), `opm.exe` plus its DLL closure (Windows),
  or `opm.app` with bundled dylibs (macOS);
- `LICENSE`, `NOTICE`, `README.md`, `BUILDING.md` and `CHANGELOG.md`;
- `INSTALL.txt`, generated by the packager with the platform requirements
  (GTK ≥ 4.10 shared libraries and the Ubuntu 24.04 build host on Linux;
  Windows 10/11 and the POSIX-shell requirement for running pipelines on
  Windows; Apple Silicon, bundled GTK and the Gatekeeper note on macOS);
- `third-party/`: one directory per registry dependency with its license
  files, `inventory.json` (name, version, license and repository of every
  dependency), and `minmark-Apache-2.0.txt` — the Apache-2.0 license text
  covering the code derived from minmark, copied explicitly from the
  repository's `third-party/` directory because its sources are not a cargo
  dependency (path dependencies carry no license files and are skipped);
- `shared-libraries.txt`: the shared libraries the binary actually uses —
  the `ldd` output on Linux (packaging fails on any "not found"), the
  copied DLL names with their source paths on Windows, and the `otool -L`
  listing of every image in the bundle on macOS.

Platform specifics:

- **Linux**: a plain `.tar.gz` whose `opm` binary is built on Ubuntu 24.04;
  it is not a static or universally portable executable, and `INSTALL.txt`
  says so.
- **Windows**: the ZIP is portable (unzip anywhere, run `opm.exe`, the GTK 4
  DLLs travel beside it); the MSI installs per machine under Program Files
  with a Start Menu shortcut. The DLL closure comes from the PE import and
  delay-import tables of `opm.exe`, and the staged executable is launched
  for 15 seconds before packaging to rule out missing DLLs.
- **macOS**: `opm.app` carries its non-system dylibs in
  `Contents/Frameworks` with paths rewritten to
  `@executable_path`/`@loader_path`; the `.dmg` adds an `/Applications`
  symlink so the stage can be dragged there.

## Checksums

Each packager writes `dist/SHA256SUMS` with one `sha256` line per artifact
of its platform. The release workflow concatenates the three platform files
and runs `sha256sum --check` over the merged set before creating the draft,
so a broken upload never reaches a release. Verify locally with:

```sh
(cd dist && sha256sum --check SHA256SUMS)
```

`SHA256SUMS` is published with the release assets; verify downloaded files
against it.

## Maintainer notes

- **WiX GUIDs are stable constants.** The MSI `UpgradeCode` lives in
  `scripts/package-windows.py` as the constant `MSI_UPGRADE_CODE`,
  generated once for opm and never taken from any other project. It defines
  the upgrade chain that `<MajorUpgrade>` matches: never regenerate the
  `UpgradeCode` (a fresh one installs a second copy beside the previous
  version instead of upgrading it) and never reuse one from another
  installer. The MSI `ProductCode`/`PackageCode` are intentionally
  auto-generated per build — the standard WiX `MajorUpgrade` convention, not
  drift.
- **macOS is ad-hoc signed only.** `scripts/package-macos.py` signs dylibs,
  binary and bundle with `codesign --sign -`. Developer ID signing and
  notarization are pending, so Gatekeeper warns on first launch;
  `INSTALL.txt` documents the right-click > Open workaround and the
  `xattr -dr com.apple.quarantine opm.app` escape hatch. Do not claim a
  signed or notarized build in the release notes until that work lands.
- **The Windows MSI is unsigned.** No Authenticode signing step exists in
  `scripts/package-windows.py`; Windows SmartScreen may warn on first run.
  The portable ZIP carries the same unsigned `opm.exe`.
- **Checksums always ship.** Every published release must include
  `SHA256SUMS` covering every asset, and the `publish` job's
  `sha256sum --check` must pass before the draft is created.

## Preparing a release

Follow [Cutting a release](CI.md#cutting-a-release): keep both Cargo
manifests on the same version, move the `Unreleased` changelog entries to
the version and date, merge the release pull request after CI, tag with
`git tag -a v<v> -m 'opm <v>'`, review the draft, and publish it manually
(the prerelease flag is set by hand).
